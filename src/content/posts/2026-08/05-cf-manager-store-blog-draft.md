## 正文

### 01 ｜ 一个小需求，和它背后的"从零搭建"

先说个真事。有天我盯着自己的几个站点，心想：要不整个状态页吧？哪个挂了能第一时间知道，最好还能给访客看个公开页面。

要是放在以前，这事儿得这么干：打开 Cloudflare 文档，新建一个 Worker；再建个 D1 数据库存监控记录，写建表 SQL；绑个域名；然后写前端页面把它展示出来……一套下来，少说半小时，还容易踩坑。

现在呢？我打开 cf-manager 的 Store 页，搜 "UptimeFlare"，看一眼它要的绑定，点一下部署，起身接杯水回来——状态页已经在线了。

这种"偷懒"的快乐，是我在把面板跑起来之后，最想跟你们唠的部分。前面两篇咱们把面板的能力和架构聊得差不多了，这篇不再重复那些，专门讲一个东西：**Store 模板市场，以及怎么用它把"搭服务"变成"选服务"**。

### 02 ｜ Store 模板市场，到底是个啥

一句话讲清楚：cf-manager 内置了一个官方的模板源，叫 **cf-store**。面板里的 Store 页，会自动从 `https://cf-store.surge.sh/catalog.json` 拉取一份"可一键部署清单"。

这份清单现在里有 **65 个模板**，覆盖 Worker、Pages、还有 Hybrid（双模）三类。类型上大致分这些：基础演示类（hello-world、kv-demo、d1-demo）、隧道/代理/加速类（edgetunnel、gh-proxy、cf-proxy-ex 等）、短链类（sink、linklet、KV UrlShort）、图床类（img-mom、Telegraph-Image、PixR2）、临时邮箱类（smail、MoeMail、cloudflare-temp-email）、文件分享类（丁丁快传 dingding、cf-files-sharing）、监控状态页类（UptimeFlare、cf-workers-status-page、SSL Certificate Monitor）、博客/内容类（cloudflare-workers-blog、gins-blog）、笔记类，还有一大票 AI/工具类（webhook-debugger、ip-api、deeplx、chatgpt-telegram-workers、whisper-cloudflare……）以及订阅管理类（sublink-worker、subpool-worker）。

你不用 clone 任何仓库，也不用记命令，更不用配一堆环境变量。装好 cf-manager 之后（这部分前面写过，这里不展开了），Store 页已经帮你把"货架上有啥"同步好了。

底子一句话带过：这份清单由 `catalog.json` 生成，旁边配了 `catalog.schema.json` 做 JSON Schema 校验保证格式不出错，模板源码放在 `templates/<id>/` 目录里。你只需要关心一件事——**我要哪个**。

### 03 ｜ 怎么用：五个动作，从货架到上线

在 Web 面板里，整个流程其实就五步，全是点：

1. **打开 Store 页**。进来它会自动调一次同步接口（默认源），把清单拉下来。这一步基本是无感的，你甚至感觉不到它在干活。
2. **看模板列表**。可以按类目翻，也可以直接搜关键词。比如输入"短链""图床""状态页"，都能精准过滤。
3. **点开一个模板**，重点看它的 **bindings**（绑定）要求。模板需要的资源分这几类：KV、D1、R2、AI、var（环境变量）。注意一个坑：变量名必须全大写。D1 类型的绑定还允许带一段 `initSql`（建表语句）。好消息是——cf-manager 会帮你**自动创建或复用**这些绑定，不用你手动去 Cloudflare 后台一个个建。
4. **点一键部署**。面板会把代码和绑定一起推到你的 Cloudflare 账户上。
5. **验证**。部署完打开分配到的地址，确认能正常跑，就完事了。

另外提一句：上游仓库更新了模板之后，你这边不会自动变。想看到新货，在 Store 页点一下"刷新"按钮重新拉一次就行。

**备用源切换**：偶尔 surge.sh 这个源会抽风，加载不出来。别急，在 Store 页把源地址换成 GitHub 原始地址 `https://raw.githubusercontent.com/hefy2027/cf-store/main/catalog.json` 就能继续用。两套源互为备份，这也算是作者埋的容错设计。

### 04 ｜ 实战 Walkthrough：给站点装个状态页（UptimeFlare）

光说步骤太虚，咱们走一遍最实用的一个——**UptimeFlare**，一个无服务器宕机监控 + 状态页模板，数据存在 D1 里。

- **挑模板**：在 Store 页搜 "UptimeFlare"，点开。
- **看 bindings**：在部署确认页，你会看到一个 D1 绑定的要求，而且带了初始化 SQL（建监控记录表）。这时候 cf-manager 会去查：你名下有没有这个 D1？没有就帮你建一个；之前建过同名的，它就直接复用。你几乎不用动手。
- **填配置**：模板本身要你填要监控的站点列表（比如你那几个域名）。这部分跟着页面提示走就行，是模板自己的配置项，不是 cf-manager 的。
- **一键部署**：点下去，面板把 Worker + D1 一起推上去。
- **验证**：打开状态页地址，能看到监控项、响应时间曲线和历史记录。以后哪个站点挂了，页面会变红，还能接通知。

整个过程，从搜到上线，我没离开过面板，也没敲一行命令。这就是模板市场存在的意义。

### 05 ｜ 再顺手一个：短链 / 图床，展示"广度"

如果你觉得状态页还不够"偷懒"，再看两个轻量的，感受一下覆盖面：

- **短链 sink**：在 Store 搜 "sink"，点开。它依赖一个 KV 来存"短码 → 长链接"的映射。cf-manager 自动帮你建好 KV 绑定，点部署，之后给长链接贴个自己域名的短后缀就能用。
- **图床 PixR2**：搜 "PixR2"，它依赖 R2 存图片。绑好 R2（按页面提示确认绑定或自动创建），一键部署，你就拥有了一个挂在自己域名下的图床。

你看，一个 KV、一个 R2，类型不同，但操作路径一模一样：**选模板 → 看 bindings → 点部署 → 验证**。这种统一体验，才是"市场"这两个字值钱的地方。（注：图床、短链都别选 text2img——那个作者单独写过文生图专题了。）

### 06 ｜ 踩坑与注意：少走点弯路

用了一阵子，几个坑得提前说：

- **surge.sh 源偶发不可用**：上面提过，直接切 GitHub 原始源就行，别卡在这一步。
- **bindings 自动创建 vs 需要手动**：绝大部分 KV/D1/R2/AI/var 会帮你自动建或复用，但个别模板可能要求你先在 Cloudflare 侧准备好特定资源（比如某个特定名称的 R2 桶）。页面上都会写清楚，跟着提示走。
- **第三方模板要自己审**：cf-store 是官方源，但里面大量模板来自社区或第三方开源项目。部署前最好扫一眼源码，确认逻辑确实是你要的，别闭眼点。
- **⚠️ 合规红线（重要）**：模板市场里包含**部分代理类、订阅管理类模板**。部署前请确认你的用途合规、遵守 Cloudflare 服务条款（ToS）；第三方模板需自行审查源码；**只用于你自有或已获授权的账户**。这一点和 cf-manager 主仓库的合规声明是一致的，咱们用着爽，也得用得干净。

### 07 ｜ 收个尾，顺便剧个透

写到这，你应该能感觉到：cf-manager 真正"偷懒"的地方，不在它能管多少账户（那是基础），而在 Store 这种**把别人造好的轮子直接端到你面前**的设计。65 个模板不是终点，它本质是一个开放目录——谁都能往上提交好用的 Worker/Pages，你也随时能刷新出新的玩法。

下一篇，我打算往"细活"里钻：隧道管理怎么一键回源、规则引擎怎么用表达式挡掉恶心流量、浏览器渲染又能玩出什么花。这些是面板里更"硬核"但也更省心的能力，咱们下回拆。

如果你这篇看完就想上手，记住最快的路径就一句话：**打开 Store 页，搜你要的东西，点部署。** 剩下的，交给面板。
